These notes ask as many questions as they answer, follow different styles and are often terse.

# Notes by Topic

## Practical AI in Pipelines

### Current state in studios

- Face detection models trained in house.
- `[?]` is doing use/manipulate/stitch code for 3DGS.
  - LoRA + AI used in practical pipelines, built in-house. Merging of stage and traditional VFX.
- Exploring render optimisation and prediction, layout, USD analysis.
  - Ollama models, a Rust harness framework, in-memory RAG that can construct reasonable queries against USD.

### Code generation and harnesses

- For code generation, how many are maximising throughput?
  - Gastown goes fast, but the output has a lot of problems.
  - Multi-model architectures (mixture of agents, orchestrator + role-based agents) are easy with a simple harness, but "oh my pi" (omp) seems to be able to go much broader in agent count, with persistence.
  - LRIG `[?]` - framework for writing harnesses.
- How hard are people working to specify outputs, tasks and roles?
  - It needs extensive work and detail.
  - "Superpowers" is a good skill baseline to work off as a template.
- How many are building harnesses themselves?
  - Hermes - harness with self-improving skills.
  - With skills, there's still looseness in instruction following, but with harnesses we can set harder rules.
- How do you leverage Ops teams when Production wants to move fast?
  - People are responsible for loads, not AI.
  - Exclusive responsibility of people with code review capability to own and maintain tools.
  - Example of commercial flights: autopilot is good only in normal, non-critical situations.
  - Redundancy and problems with vibe code **must** be code reviewed.

### Review, guardrails and auditing

- Tests and guardrails need to be built into your code review and agentic helper scripts.
- K-shaped developer economy: how can you even keep up as a maintainer vs the prompters?
  - You need to classify the code in terms of priority and security context / priority.
  - Bots can do the pre-assessment and leave you notes for the maintainer.
  - Code can and maybe should be more ephemeral.
    - Deletion can also be done fast.
- Analytics harness to audit all agents or humans who use agentic code.
  - Keep AI sessions' logs and you can use those to audit what is popping up and from whom.
  - Can't rely on an agent to self-audit.
  - Building testing frameworks to prevent regression.
    - How do you unit test a model whose answers are not deterministic?
    - OpenObserve could work in this context.
    - Once you have a faithfulness score... what do you do with it? What now?
- Layoffs in this industry mean less humans in the loop.
  - Makes the problem worse.

### Helping artists, tooling and MCP

- In the pipeline space, who's had success in providing agentic tooling that helps artists understand what's going wrong when stuff goes wrong?
  - Feeding render logs into AI is phenomenal.
  - Asset management system can aggregate comments from the version list.
  - Anyone have an MCP for a Maya session or USD? Not yet. Is this useful?
    - LLMs are not great at applying a full API - need more focused tools.
    - Natural language search works better for LLMs. Patch them into human-language tooling - it's what they know best?
    - CLI better than MCP for LLMs too.
      - Some things can expose both.
      - Command lines, e.g. GitLab, obsolete the MCP.
        - Except you lose tracebacks.
- Don't put it in a position where it needs to be right all the time. If you need scale and repeatability, you need to write actual code.
  - Agents are good at rewriting APIs, etc. This can facilitate removing the agent from the end-workflow.
- Some languages, e.g. Rust, can be harder to collab with an agent on.
- Using LLMs to process show data from the audit log of Shotgrid.
  - Several studios trying to ask natural language questions against show data.
  - Ripe ground to fine-tune a model against.

### Dependence, trust and security

- Becoming dependent on the bot.
  - Trust is super important - and the second wave of adopters will have _too much_ faith in the system!
  - Research isn't done yet - future moves could invalidate your whole harness/workflow.
- Too easy to get caught up, but unsexy tasks can make AI super useful in pipeline - looking at and resolving pipeline problems should take priority over pushing out features.
  - AI in the ticket system (categorising, solving).
  - AI in code reviews.
- Why is it so hard to get people to write tests?
  - Put things in cron and get it done automagically.
- If you can't take the time to write it, it's not worth reading.
  - Review at least.
- Authorisation: RBAC and user auth is not controlled well.
  - Harnesses have way too global a set of access controls, and too permanent "Allow all".
  - Lack of fine-grained understanding of what an agent even is means security becomes more of a problem.

## Multi-Site Pipeline

### Current situation

- People all over, working from home.
- Skydance: Madrid, NYC, (some) LA.
  - Used Avere at first - not successful for workflows.
  - In-house sync was also not successful.
  - Qumulo CDF - a few months, but so far successful (synced on demand).
- All workstations close to artists - needed for `[?UDI]`/VR (Disney attractions).
  - Next to actual display they are driving.
  - Mostly comp work so I/O is nearby.
  - So everything is distributed and an entire "datacenter" with the artist.
  - Need better ways of syncing - don't have enough bandwidth to sync in real time.
    - Sometimes Starlinks bonded together for cruise ships.
    - Can't use internet cloud - in ocean!
    - So two primary sites solved but not satellites.
- ArtJail - commercials.
  - NY, LA, Toronto.
  - Sole pipeline resource at company, trying to keep NY/LA working together.
  - `[?]` might need intelligent warm up.
- EA - pull down from Perforce the things you want to work on. Everything was in the package. `[?Redels]` for prebaking. The game size is in TB, not PB - wouldn't work for film projects.
- VDI: host all locally until end of life.
- Parsec folks have started a new company?
- Cinesite has regional datacenters.
  - Only do data sync between 2 sites at a time.
- Can get complicated quickly if there are multiple solutions at different sites.
- 3-4 main locations + more work from site to site - event-driven sync.
  - Moving to a hybrid "pull" system based on USD + custom resolver, e.g. images everyplace is always synced.
- Have to evaluate the USD to know what data to pull (except leaves, which are small).
  - Cinesite `[?]` uses a relational database to track USD dependencies.
  - Data you need is a small subset of all the data.
- Metadata system can track dependencies but it is not composition-aware enough to be specific enough.
- What is this particular file depended on by? What happens if I archive this file? What will break?
- Rez is great, but you need the filesystem. Lots of small files not great over SMB. Conversely, a 10-20 GB Rez package (with a packaging plugin).
- ComfyUI updates happen 100s of times a day.
- Training and pushing new models every night (?!) but hundreds of TB. Model engine can recognize if the world has changed.

### Databases

- Postgres - 1 main + many read replicas.
- MySQL had too much overhead.
- `[?Tomkat]` - can't handle.
- "Ring" of databases where each RW database updates the next one and so on.
  - But delay of an hour is OK.
- Workflow - send file, approve (requires file transfer to complete), then send on.
- When checking in data, the database requires checks before commit.
- For production tracking, use a local SQL cache of the production database and sync on reattach (Shotgrid is the source of truth).
- Redis cache per site.
- **DO NOT** put non-production data in the production database!
  - `[?Bogged down]` entities.
  - Can't do standard database stuff.
  - May expose data when migrating to Shotgun Cloud.

## Build or Improve Legacy Tools

- Large (4) studios: change management, Rez went pretty smoothly. Agents on Git to better transition.
- Engineering problems easy. People problem was more difficult.
- Using coding tools to switch to better languages.
- Use "influencers" inside a studio to help adoption and testing.
- Use agents to update dependencies.
- A lot of Rez adoption. Line can be drawn by OS-supplied or tools developed internally.
- What drives changes? It's a mix. Can be performance.
- Squish for testing Qt/UI testing.
- Studios tend to have better success iterating on a tool than swap and replace.
- Semantic versioning only works if devs are consistent.
- Gitflow (tool) works really well.
- At a slower cadence, time-based versioning (ex: 2025.1) works really well.

## Reducing the Boundary Between Production and Technology

### Grievances

- Translating terms in a way that production understands them.
  - Understanding the tech.
  - Trust - build trust with tech and production so they know production is in good hands.

### Notes

- Production sometimes doesn't know what to ask for.
- Start a conversation with production and build trust.
- Bring in technology early in the conversation so false promises aren't made.
- Game of telephone is common because there are too many cooks in the kitchen.
- Always double check your understanding.
- If you haven't used tools on a daily basis, you are less likely to see the issues with it.
- Changing scope is problematic because the definition of the issues is lost.
- Spreadsheets are easier to understand than other more complex tools.
- Separate support channel for production.
- Shadow a tech director for a day to get a sense of what production does.
- Solve an issue and build rapport.
- Establish a path to raise issues, or accept the burden on your engineers.
- Communicate in terms of impact.
- Influence, scare or excite production about a change (tech debt).
- Make it difficult for people to do the wrong thing.
- Vibe-coded tools get added to an app store where the studio votes and decides which tools can get published.
  - AI = scary.
